# 申し送り: ファイル読み書きツールの不具合と回避策

作成日: 2026-07-15
対象セッション: `feature/design-revision`（デザイン見直し作業）
目的: 同環境（Windows / Claude Code）で作業する後任が同じ罠にはまらないための記録。

---

## 1. 結論（先に読む）

- **ファイル編集自体は正しく実ファイル（git 作業ツリー）に反映された。** 不具合はいずれも「ツールの表示・応答レイヤー」で発生したもので、ディスク上のファイルは健全だった。
- ただし読み取り・検証系ツールが**断続的に嘘・欠落を返す**ため、素朴に信じると「編集できていない」「実物と違う内容」に見えて混乱する。
- **`awk` 直読を「正」とし、`Edit` の照合に使う運用**に切り替えたら安定して作業できた（下記 手順）。

---

## 2. 観測した不具合

| ツール | 症状 |
|---|---|
| `Read` | 一部ファイル（特に `.cs`、行数の多いファイル）で、実物と異なる**要約／プレースホルダ内容**を返す。例: `ThresholdMarkerOverlay.cs` の実体は `SetMarkers(IReadOnlyList<...>){...}` だが、Read は `SetMarkers(...)` と省略形を返した。エラーではなく“それらしい嘘”を返すのが最も危険。 |
| `Bash` | 出力の**行重複・欠落・混線**が頻発。特に「複数コマンドを `;`/`&&` で連結」「長い出力」「`grep`/`awk` のパイプ」で悪化。同じ行が何十回も繰り返される、途中で切れる、前のコマンドの出力が混ざる等。 |
| `Write` | 応答テキストが壊れることがある（"The file has been. The file has been..." 等）。ただし**実ファイルへの書き込み自体は成功**していた。 |
| `Glob` / `Grep` | 実在ファイルを「見つからない」と返すことがあった。特にセッション開始後に追加されたファイル・日本語名ファイルで発生。 |
| `PowerShell` | 一時的にコマンドが実行されず**エコーバックのみ**になる。`Select-Object -Last N` が末尾でなく中間を返すズレも発生。コマンド文字列に**日本語（マルチバイト）を含むと壊れやすい**（パスが `---` に化けた）。 |

補足:
- 同じファイル・同じコマンドでも、実行タイミングで成功したり壊れたりと**再現性が低い**（＝恒久故障ではなく間欠的なグリッチ）。
- `Read` は XAML では概ね実体を返したが、`.cs` で嘘を返す頻度が高かった。ファイル種別で確実に切り分けられるわけではないので、**Read は常に疑う**のが安全。

---

## 3. 有効だった回避策（推奨ワークフロー）

1. **実データの取得は `awk` の直読を使う**（`Read` を信用しない）。
   - 範囲指定・単一コマンドが安定: `awk 'NR>=A && NR<=B { printf "%d|%s\n", NR, $0 }' FILE`
   - 末尾行が重複表示されるグリッチはあるが、中身の把握には十分。
2. **`Edit` の `old_string` は必ず `awk` 直読の実データから作る。** `Read` 出力をコピペしない（嘘データだと `not found` か誤爆になる）。
3. **`Edit` 後は `awk` で該当箇所を再取得して照合**（CLAUDE.md の「編集後検証」を担保）。`Edit` の成功応答テキストは壊れることがあるので鵜呑みにしない。
4. **インデント確認は `awk` の `match()/RLENGTH`** が正確: `awk '{ match($0,/^ */); print RLENGTH }'`。`cat -A` は先頭に +1 空白のズレを出したことがあり不正確。
5. **git 確認は単独コマンドで。** `git status --short` / `git diff --stat FILE` を単独実行すると確実。複数コマンド連結だと出力が欠落する。
6. **XML/XAML の構文健全性は PowerShell の `[xml]` キャストで検証**（ASCII パスで実行）:
   `[xml](Get-Content -LiteralPath $f -Raw -Encoding UTF8)` が例外を出さなければ well-formed。
7. **Bash は「`echo` マーカーで挟む」「1コマンド1目的」「短い範囲」** にすると通りやすい。
8. **ファイル名・パスは ASCII を優先。** 日本語名は `Read`/`Glob` が拾えないことがあった（本資料を ASCII 名にしたのもこのため）。一時ファイルを ASCII 名でコピーして読むのも有効。

---

## 4. 確認できた事実（安心材料）

- `git status --short` で対象ファイルが `M` になり、`git diff --stat` で行数変化を確認 → **編集は実ディスクに届いている**。
- `feature/design-revision` ブランチ作成も実リポジトリに反映済み。
- したがって、ツールのグリッチは**表示・応答の問題であって、データ破壊ではない**。最終確認は必ず `git` と `awk` 直読、そしてビルドで行うこと。

---

## 5. 次担当者への推奨

- 作業前に「`awk` 直読 → `Edit` → `awk` 照合 → `git diff` 確認」の型を最初から使う。
- 大きな読み取りを `Read` 一発で済ませようとしない（嘘データを掴む）。範囲分割で `awk`。
- 不安が残るときは、`Read`/`Bash` の出力同士ではなく **`git` と `awk` を突き合わせて**事実を確定する。
- 症状が悪化して手が止まる場合は、Claude Code の**プロセス再起動**を試す価値がある（間欠グリッチのため改善する可能性）。
