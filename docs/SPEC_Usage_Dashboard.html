1目的とスコープ

1.1目的

Claude Code と Codex を日常的に使っているが、どのプロジェクトに、どれだけのトークンと時間を使ったかが分からない。 既存の AIUsageOverlay は「いま残りいくつか」をリアルタイムに出すツールで、過去を振り返る用途を持たない。

困りごとは 3 つある。

(1) 配分が見えない。 週の枠を使い切ったとき、それがどの作業に消えたのかを説明できない。 プロジェクトごとの内訳が出れば、重い作業を軽量モデルへ回す判断ができる。

(2) 何に時間を使ったかが分からない。 体感では「調査ばかりしていた」と思っても、 実際に調査・実装・テストのどこに寄っていたかは記憶に頼っている。

(3) サブエージェントの消費が見えない。 実測では、同じプロジェクトの同じ時間帯に動いた 2 つのサブエージェントが、2,166 万トークンと 17 万トークン（125 倍差）を消費していた（付録 B.1）。 サブエージェントを畳んだ一覧だけを見ても、どれが重かったのかを掴めない。

要確認

要確認: 親セッション単体の消費は実測できていない。 付録 B.1 に載せた 2 行はいずれもサブエージェントであり、親の値ではない。 「親より子が重い」という仮説は B0 で確かめる（→ Q7）。

これらはすでにローカルの履歴ファイルに記録されている。実行時に新たな計測を仕込む必要はない。 本機能は、その履歴を読んで 1 枚の HTML レポートにするものである。

設計上の判断

本設計は実測に基づく。Codex 505 ファイル・593 MB・269,076 行、および Claude Code のセッション 1 件を 実際にパースして得た結果を付録 B に置いた。本文中の数値はすべてそこに出典がある。

3.2責務の分界

集計は C# 側、描画は HTML 側に置く。両者を混ぜない。

  • C# は履歴を読み、正規化し、集計し、数値が確定した状態の JSON を HTML に埋め込む
  • HTML は埋め込まれた JSON を読んで描画・絞り込み・並べ替えを行う。再集計はしない
  • HTML 側では履歴ファイルを一切参照しない。生成後は単体で完結する

この分界により、レポートを他人に渡しても動く。また、集計ロジックの検証は C# 側の単体テストで完結する。

注意

注意: この分界は「HTML から履歴を読み直す機能を作れない」ことを意味する。 Rev 1.0 ではセッションのターン別明細を「開いたときに元ファイルを再パースする」と書いていたが、 自己完結 HTML から C# を呼び戻す経路は存在しない。Rev 1.1 で撤回した（→ N9 / 付録 D）。 分界を宣言したなら、その帰結として作れなくなる機能を先に洗い出しておく。

描画を HTML に寄せるのは、WPF でグラフを実装する手間を避けるためだけではない。 レポートは「配って読ませるもの」であり、アプリを持っていない相手にも開ける必要がある。 WPF 画面にすると、その要件を満たせない。

3.3方式選択

3.3.1出力形態

方式 内容 判定
A: WPF に分析画面を追加 既存アプリ内に新規ウィンドウを作る 不採用
B: 自己完結 HTML を生成して既定ブラウザで開く 集計は C#、描画は HTML 採用
C: 分析専用の別 exe 新規 WPF アプリを作る 不採用
設計上の判断

方式 A を採らない理由: グラフ・表の絞り込み・並べ替えを WPF で実装する量が大きい割に、 得られるのは「アプリ内で見られる」ことだけである。しかもレポートを他人に渡せない。 リアルタイム監視が本業のアプリに、数十秒かかる集計処理を同居させる設計上の理由もない。

方式 C を採らない理由: 履歴の場所・設定の持ち方・配布経路がすべて二重になる。 既存 exe にメニュー 1 つ足すだけで済むものを、別アプリにする理由が無い。

3.3.2キャッシュの実体

方式 内容 判定
A: SQLite（Microsoft.Data.Sqlite） 明細行まで保持し SQL で集計 不採用（Rev 1.0 では）
B: JSON ファイル セッション単位の集計済みレコードを 1 ファイルに保持 採用
C: キャッシュなし・都度全スキャン 状態を持たない 不採用
設計上の判断

方式 B を採る理由: 保持するのは明細ではなくセッション単位の集計済みレコードなので、 行数は「履歴の行数」ではなく「セッション数」になる。実測時点で 1,099 セッション。 1 件あたり約 900 バイト（UUID・ISO8601・日本語 64 文字を実長で見積もる）に、 差分判定用のフルパス 1,099 件を加えて 1.3〜1.5 MB 規模になる。この規模に SQL エンジンは要らない。

注意: 日本語の指示文は既定の JavaScriptEncoder で \uXXXX（1 文字 6 バイト）へ展開される。 64 文字なら 384 バイトになり、レコードの約 4 割を占める。 既存コードは JsonSerializerOptions.Encoder を設定していない（UsageService.cs / UsageHistoryService.cs）。 本キャッシュも既定のままとし、UnsafeRelaxedJsonEscaping は使わない。 サイズ削減より、エスケープ規則を 1 つに保つ方を採る。

方式 A を退けた理由: self-contained 単一 exe の配布形態に、RID ごとのネイティブ SQLite が加わる。 現在の外部依存は WebView2 のみ（AIUsageOverlay.csproj）で、その単純さを崩す対価に見合わない。 ただしセッション数が 1 万件を超える、あるいは明細行の保持が必要になった時点で A へ移行する（→ C4）。

既存の JSON ファイルは settings.json / usage.json / history.json の 3 つである （history.json は UsageHistoryService が書く使用率のリングバッファ）。 本キャッシュは 4 つ目として session-stats-cache.json を置く。

制約

制約: 既存 2 サービスの WriteIndented は true（UsageService）と false（UsageHistoryService）で 揃っていない。「既存に書式を揃える」という言い方はできない。 本キャッシュは WriteIndented = false とする（サイズを優先）。→ C8

方式 C を退けた理由: 実測で Codex 505 ファイル 593 MB の全スキャンに 21.6 秒を要した（付録 B）。 Claude Code 594 ファイルを加えると倍近くになる見込みで、レポートを開くたびに待たされる。 加えて、履歴ファイルは各ツールの保持期間設定で削除され得るため、 キャッシュを持たないと過去分が復元不能なまま失われる。

R4 レポートの外部送信 HTML は外部参照を一切持たない。スクリプトからの通信も行わない 生成された HTML ファイル自体を利用者が転送することは防げない

5.2Codex — session_id は会話ツリーのルートであってセッションではない

設計上の判断

Rev 1.2 で全面的に差し替えた。 Rev 1.1 は「fork のたびに元履歴が丸ごと複製される」という 前提に立ち、session_id を鍵にして最大値の 1 件だけを採る規則にしていた。 B0 の実機確認（→ 10.2.2）でこの前提が誤りと分かったため、規則ごと入れ替えた。

Codex は 1 つの会話ツリーから派生したスレッド（fork とサブエージェント）に、 同じ session_id を与える。 session_id はツリーのルート ID であり、セッションの識別子ではない。 スレッド固有の識別子は session_meta.id である。

実測（540 ファイル / 2026-09-01 時点）:

同一 session_id のファイル群は複製ではない。 user_message の系列を全ペアで比較したところ、 検査した 12 グループすべてで prefix 関係が成立せず、内容が枝分かれしていた。

fork 先は累積トークンをリセットして 0 から始まる。 親を解決できた 390 スレッドのうち、 子の初回累積が親の累積の半分以上だったのは 3 件のみで、387 件は 1〜2 万トークン （自分の初期コンテキスト相当）から始まっていた。 つまり各スレッドの total_token_usage は、そのスレッド固有の消費である。

重複計上は存在しない。 内容シグネチャ（user_message 列 + 最終累積 + 行数）が一致する 複製ファイルは 0 組、全行が同一 timestamp のファイルも 0 件だった。 id 単位の合算と内容一意化後の合算は完全に一致した（差 0）。

採用する規則。 session_meta.id（スレッド固有 ID）を鍵とし、すべてのスレッドを別々に集計する。 session_id は親子表示のグルーピングにのみ使い、重複排除には使わない。

消えるのは主にサブエージェント分である（thread_source 別の内訳は subagent 5,306,505,158 / user 1,894,521,090）。 サブエージェントは「重複」ではなく「独立した消費者」として扱う。 1.1 の動機(3)は、まさにこの消費を見えるようにすることだった。

設計上の判断

教訓: ID の共有だけを根拠に除外規則を作らない。「重複しているはず」という仮説は、 内容シグネチャの一致で裏を取ってから規則にする。裏取りを省くと、実在する消費を捨てる。

時刻の種類が 1 つしかないセッションは経過時間の算出から除外する（測定不可として扱う）。 トークンは有効なので集計には含める。画面上は「測定不可」バッジを出す（→ 8.4）。 実機の 540 ファイルでは該当が 0 件だったが、規則としては残す。

5.3プロジェクトの正規化

正規化の規則（この順で適用する）:

# 処理

2 区切りを \ に統一（/ を含む記録があり得る）

5.4親子の紐付け

指標 定義
単独値 そのセッションだけの消費
累計値 そのセッションと、配下の全サブエージェントの合計

プロジェクト別の集計には単独値の総和を使う（累計値を足すと二重計上になる）。 セッション一覧では親行に累計値、子行に単独値を出し、子は既定で畳む（→ 8.4）。

7.1トークン指標の定義

キャッシュ読込は実際のモデル処理には効くが、課金・レート制限への寄与は小さい。 両方を別々に出す。片方だけを「トークン数」と呼ばない。

指標 Claude Code Codex
課金相当トークン input + cache_creation + output (input − cached_input) + output
総処理トークン 上記 + cache_read input + output（= total_tokens）
キャッシュ読込 cache_read_input_tokens cached_input_tokens
推論トークン 記録なし（- を表示） reasoning_output_tokens（output の内数として別掲）

実測では総処理トークンの 95〜97% がキャッシュ読込だった。 単純合計を「使用量」として出すと、実感（レート制限の消費）と桁が合わない。 概要画面では課金相当を主指標とし、総処理トークンは併記に留める（→ 8.2）。

要確認

要確認: Codex の課金相当を (input − cached_input) + output としたのは、 cached_input が input の内数であるという前提に立つ。この前提は未検証。 → Q1

7.2時間の定義

指標 定義

経過時間だけを出す。推定は行わない。

Rev 1.0 では、隣接する記録の時刻差からしきい値超の空白を除いた「アクティブ時間」を出す設計にしていた。 Rev 1.1 で取り下げた。理由は 3 つある。

  • しきい値（120 秒）に実測の根拠が無く、実装前に潰すべき Q を 1 つ増やしていた
  • 長時間かかるビルド・テストが「離席」として除外され、テストフェーズだけが系統的に過小になる
  • 要求は「使用量の統計・プロジェクト分析・履歴」であり、経過時間で足りる

空白時間の分布を測ってから入れる。測らずに閾値を置かない（→ 付録 D）。

8.7埋め込み JSON のエスケープ

集計結果の JSON には、履歴由来の任意文字列（指示文・フルパス・未分類コマンド）が入る。 <script> に素で書き出すと、指示文に </script> が含まれた時点で HTML が破綻し、 任意スクリプトが実行され得る（→ R6）。

事項 決定
埋め込み先 <script type="application/json" id="report-data">…</script>。実行可能な <script> に直接書かない
読み出し JSON.parse(document.getElementById('report-data').textContent)
追加エスケープ JSON 化した文字列に対し < → <、> → >、& → &、\u2028 / \u2029 を置換する
適用箇所 1 箇所に集約する。 埋め込み処理を通らない書き出し経路を作らない
検証 T14 で </script> <!-- \u2028 を含む合成データを通す

< を潰せば </script> は成立しない。& は HTML エンティティ解釈、\u2028 / \u2029 は JavaScript の行終端子として扱われるため、いずれも JSON としては合法だが埋め込むと壊れる。
