## 1 目的とスコープ

### 1.1 目的

Claude Code と Codex を日常的に使っているが、**どのプロジェクトに、どれだけのトークンと時間を使ったかが分からない。**
既存の `AIUsageOverlay` は「いま残りいくつか」をリアルタイムに出すツールで、過去を振り返る用途を持たない。

困りごとは 3 つある。

**(1) 配分が見えない。** 週の枠を使い切ったとき、それがどの作業に消えたのかを説明できない。
プロジェクトごとの内訳が出れば、重い作業を軽量モデルへ回す判断ができる。

**(2) 何に時間を使ったかが分からない。** 体感では「調査ばかりしていた」と思っても、
実際に調査・実装・テストのどこに寄っていたかは記憶に頼っている。

**(3) サブエージェントの消費が見えない。** 実測では、同じプロジェクトの同じ時間帯に動いた
2 つのサブエージェントが、2,166 万トークンと 17 万トークン（**125 倍差**）を消費していた（付録 B.1）。
サブエージェントを畳んだ一覧だけを見ても、どれが重かったのかを掴めない。

> 要確認: **親セッション単体の消費は実測できていない。**
> 付録 B.1 に載せた 2 行はいずれもサブエージェントであり、親の値ではない。
> 「親より子が重い」という仮説は B0 で確かめる（→ Q7）。

これらは**すでにローカルの履歴ファイルに記録されている**。実行時に新たな計測を仕込む必要はない。
本機能は、その履歴を読んで 1 枚の HTML レポートにするものである。

> 本設計は実測に基づく。Codex 505 ファイル・593 MB・269,076 行、および Claude Code のセッション 1 件を
> 実際にパースして得た結果を付録 B に置いた。本文中の数値はすべてそこに出典がある。

## 2 用語

| 用語 | 意味 |
|---|---|
| 履歴ファイル | Claude Code / Codex が各セッションごとに書き出す JSONL。1 行 1 イベント |
| セッション | 1 回の対話の単位。Claude Code は 1 ファイル = 1 セッション。Codex は fork により 1 セッションが複数ファイルに複製され得る |
| サブエージェント | 親セッションから起動される子。Claude Code では `isSidechain` および `subagents/` 配下、Codex では `thread_source=subagent` で識別する |
| ターン | ユーザー発言から次のユーザー発言までの区間 |
| 課金相当トークン | 課金・レート制限に効くとみなす合計。キャッシュ読込を含めない（→ 7.1） |
| 総処理トークン | キャッシュ読込を含めた合計。実際にモデルが処理した量 |
| 経過時間 | セッションの最初の記録から最後の記録までの時間差。**人間の読み待ち・離席を含む**（→ 7.2） |
| フェーズ | 調査 / 実装 / テスト / 対話 / 未分類 の 5 区分。**ツール実行の回数で数える**（→ 7.3） |
| 分類率 | ツール実行のうちフェーズを決められた割合。**未分類を含めた母数で計算する** |
| セッション統計キャッシュ | 本機能がパース結果を保存する場所。**既存の `history.json`（使用率のリングバッファ）とは別物**（→ 6 章） |

原典側では呼び方が異なるものがある。突合のときに効くので併記する。

| 本書 | Claude Code の呼び方 | Codex の呼び方 |
|---|---|---|
| セッション ID | `sessionId` | `payload.session_id` |
| プロジェクト | `cwd` | `payload.cwd` |
| キャッシュ読込 | `cache_read_input_tokens` | `cached_input_tokens`（`input_tokens` の内数） |
| キャッシュ作成 | `cache_creation_input_tokens` | `cache_write_input_tokens` |
| 推論トークン | 記録なし | `reasoning_output_tokens`（`output_tokens` の内数） |

> 注意: Codex の `cache_write_input_tokens` は実測時点で常に 0 だった。
> **0 だからといって取り込みを省略しない。** 値が入り始めたときに黙って落ちる。
> 6 章のモデルでは `cacheCreate` として両ツール共通の枠に格納する。

**命名について。** 既存に `Services/UsageHistoryService.cs` があり、
`%AppData%\AIUsageOverlay\history.json` へ**使用率のリングバッファ**を書いている。

### 3.2 責務の分界

**集計は C# 側、描画は HTML 側に置く。両者を混ぜない。**

- C# は履歴を読み、正規化し、集計し、**数値が確定した状態の JSON を HTML に埋め込む**
- HTML は埋め込まれた JSON を読んで描画・絞り込み・並べ替えを行う。再集計はしない
- HTML 側では履歴ファイルを一切参照しない。生成後は単体で完結する

この分界により、レポートを他人に渡しても動く。また、集計ロジックの検証は C# 側の単体テストで完結する。

> 注意: **この分界は「HTML から履歴を読み直す機能を作れない」ことを意味する。**
> Rev 1.0 ではセッションのターン別明細を「開いたときに元ファイルを再パースする」と書いていたが、
> 自己完結 HTML から C# を呼び戻す経路は存在しない。Rev 1.1 で撤回した（→ N9 / 付録 D）。
> 分界を宣言したなら、その帰結として作れなくなる機能を先に洗い出しておく。

> 描画を HTML に寄せるのは、WPF でグラフを実装する手間を避けるためだけではない。
> **レポートは「配って読ませるもの」であり、アプリを持っていない相手にも開ける必要がある。**
> WPF 画面にすると、その要件を満たせない。

### 3.3 方式選択

### 3.3.1 出力形態

| 方式 | 内容 | 判定 |
|---|---|---|
| A: WPF に分析画面を追加 | 既存アプリ内に新規ウィンドウを作る | **不採用** |
| B: 自己完結 HTML を生成して既定ブラウザで開く | 集計は C#、描画は HTML | **採用** |
| C: 分析専用の別 exe | 新規 WPF アプリを作る | **不採用** |

> 方式 A を採らない理由: グラフ・表の絞り込み・並べ替えを WPF で実装する量が大きい割に、
> 得られるのは「アプリ内で見られる」ことだけである。しかもレポートを他人に渡せない。
> リアルタイム監視が本業のアプリに、数十秒かかる集計処理を同居させる設計上の理由もない。

> 方式 C を採らない理由: 履歴の場所・設定の持ち方・配布経路がすべて二重になる。
> 既存 exe にメニュー 1 つ足すだけで済むものを、別アプリにする理由が無い。

### 3.3.2 キャッシュの実体

| 方式 | 内容 | 判定 |
|---|---|---|
| A: SQLite（`Microsoft.Data.Sqlite`） | 明細行まで保持し SQL で集計 | **不採用（Rev 1.0 では）** |
| B: JSON ファイル | セッション単位の集計済みレコードを 1 ファイルに保持 | **採用** |
| C: キャッシュなし・都度全スキャン | 状態を持たない | **不採用** |

> 方式 B を採る理由: **保持するのは明細ではなくセッション単位の集計済みレコード**なので、
> 行数は「履歴の行数」ではなく「セッション数」になる。実測時点で 1,099 セッション。
> 1 件あたり約 900 バイト（UUID・ISO8601・日本語 64 文字を実長で見積もる）に、
> 差分判定用のフルパス 1,099 件を加えて **1.3〜1.5 MB 規模**になる。この規模に SQL エンジンは要らない。

> 注意: 日本語の指示文は既定の `JavaScriptEncoder` で `\uXXXX`（1 文字 6 バイト）へ展開される。
> 64 文字なら 384 バイトになり、レコードの約 4 割を占める。
> **既存コードは `JsonSerializerOptions.Encoder` を設定していない**（`UsageService.cs` / `UsageHistoryService.cs`）。
> 本キャッシュも既定のままとし、`UnsafeRelaxedJsonEscaping` は使わない。
> サイズ削減より、エスケープ規則を 1 つに保つ方を採る。

> 方式 A を退けた理由: self-contained 単一 exe の配布形態に、RID ごとのネイティブ SQLite が加わる。
> 現在の外部依存は WebView2 のみ（`AIUsageOverlay.csproj`）で、その単純さを崩す対価に見合わない。
> ただし**セッション数が 1 万件を超える、あるいは明細行の保持が必要になった時点で A へ移行する**（→ C4）。

既存の JSON ファイルは `settings.json` / `usage.json` / **`history.json`** の 3 つである
（`history.json` は `UsageHistoryService` が書く使用率のリングバッファ）。
本キャッシュは 4 つ目として `session-stats-cache.json` を置く。

> 制約: 既存 2 サービスの `WriteIndented` は `true`（`UsageService`）と `false`（`UsageHistoryService`）で
> 揃っていない。**「既存に書式を揃える」という言い方はできない。**
> 本キャッシュは `WriteIndented = false` とする（サイズを優先）。→ C8

> 方式 C を退けた理由: 実測で Codex 505 ファイル 593 MB の全スキャンに 21.6 秒を要した（付録 B）。
> Claude Code 594 ファイルを加えると倍近くになる見込みで、レポートを開くたびに待たされる。
> 加えて、履歴ファイルは各ツールの保持期間設定で削除され得るため、
> **キャッシュを持たないと過去分が復元不能なまま失われる。**

### 3.4 データフロー

```
  [1] 走査     .claude / .codex を再帰的に列挙
                 │  パス + 最終更新時刻 + サイズ をキャッシュと突合
                 ▼
  [2] 差分判定  変化のあったファイルのみ次段へ（初回は全件）
                 │
                 ▼
  [3] 読み取り  JSONL を 1 行ずつストリーム読み。全文をメモリに載せない
                 │  ├ Claude Code: message.usage / tool_use / timestamp
                 │  └ Codex:       token_count / custom_tool_call / patch_apply_end
                 ▼
  [4] 正規化    重複排除（5.1 / 5.2）→ cwd 正規化（5.3）→ 親子の紐付け
                 ▼
  [5] 分類      ツール実行をフェーズへ写像。決められないものは「未分類」
                 ▼
  [6] 保存      セッション単位の集計レコードをキャッシュへ upsert
                 ▼
  [7] 集計      期間で絞り、プロジェクト / 日 / ツール / モデル 各軸へ畳む
                 ▼
  [8] 生成      HTML テンプレートへ JSON を埋め込み（エスケープは 8.7）、ブラウザで開く
```

**[4] の正規化を [6] の保存より前に置く。** 重複を含んだままキャッシュに入れると、
後から除去しても既に混ざった集計値を分離できない。

**[2] の差分判定は読み取りの前後で 2 回行う。** Claude Code / Codex が動作中でも本機能は起動され得るため、
読んでいる最中にファイルが追記される。読了後の `(size, mtime)` を読み取り前の値と比較し、
**変わっていたらキャッシュに登録しない**（次回スキャンで読み直す）。
登録してしまうと、追記分が次の更新まで恒久的に欠落する（→ 8.6）。

### 3.5 セキュリティとプライバシー

履歴には業務上の指示文・ファイルパス・コマンドが含まれる。**レポートは人に渡す前提の成果物である**ため、
何を載せて何を載せないかを設計で決める。

| # | リスク | 対策 | 残るリスク（受容する） |
|---|---|---|---|
| R1 | 会話本文がレポートに載る | 本文は集計に使うのみ。出力するのは各セッションの最初の指示文の先頭 64 文字だけ | **その 64 文字に機密が含まれ得る。** 設定で「指示文を出力しない」を選べるようにする（→ S11 / Q5） |
| R2 | ファイルパスから業務内容が推測される | **対策しない。** 実パスをそのまま出す | **プロジェクトのフルパスがレポートに載る。** 別名機能は N10 で非スコープにした。渡す相手を選ぶ運用で受け入れる（→ C1） |
| R3 | 履歴ファイルを壊す | 読み取り専用で開く（`FileShare.ReadWrite` で共有読み） | なし |
| R4 | レポートの外部送信 | HTML は外部参照を一切持たない。スクリプトからの通信も行わない | **生成された HTML ファイル自体を利用者が転送することは防げない** |
| R5 | 認証情報の混入 | トークン・API キーらしき文字列は抽出対象に含めない（指示文の先頭 64 文字のみが対象） | 指示文の先頭にキーを貼っていた場合は載る |
| R6 | **埋め込み JSON によるスクリプト注入** | 履歴由来の文字列（指示文・パス・コマンド）を `<script>` に素で入れると、`</script>` を含む指示文で HTML が破綻し、任意スクリプトが実行され得る。8.7 のエスケープ規則で防ぐ | **エスケープ漏れが 1 箇所でもあれば成立する。** T14 で `</script>` を含む合成データを必ず通す |

> 注意: R1 と R5 は「先頭 64 文字だけなら安全」という前提に立っている。**この前提は検証していない。**
> 実運用の前に、自分の履歴で先頭 64 文字を一覧出力して目視確認する（→ T9）。

## 4 入力仕様

両ツールとも JSONL（1 行 1 JSON）である。**行単位でパースし、壊れた行はスキップして続行する。**
1 行の破損でセッション全体を捨てない。スキップ件数はデータ品質タブに出す（→ 8.5）。

### 4.1 Claude Code の履歴

**場所。** `%USERPROFILE%\.claude\projects\<プロジェクト名をエスケープした名前>\<セッションUUID>.jsonl`

**プロジェクトの特定にはディレクトリ名ではなく各行の `cwd` を使う。**

行の種別は `type` で判別する。実測サンプルでの内訳:

| `type` | 件数 | 集計での扱い |
|---|---|---|
| `assistant` | 357 | **トークンとツール実行の抽出元** |

### 4.2 Codex の履歴

**場所。** `%USERPROFILE%\.codex\sessions\YYYY\MM\DD\rollout-<ISO時刻>-<UUID>.jsonl`
日付ディレクトリに分かれるため、期間で絞る走査はディレクトリ名だけで枝刈りできる。
実測時点で 505 ファイル・593 MB・269,076 行。

行は `{"timestamp", "type", "payload"}` の形で、`type` と `payload.type` の 2 段で種別が決まる。

| `type` / `payload.type` | 集計での扱い |
|---|---|
| `session_meta` | セッション属性（cwd / session_id / fork 情報 / サブエージェント情報） |
| `event_msg` / `token_count` | **トークンの抽出元** |
| `turn_context` | モデル名 |
| `event_msg` / `user_message` | ターン境界・指示文 |
| `response_item` / `custom_tool_call`（`name=exec`） | シェル実行。フェーズ分類の材料 |
| `event_msg` / `patch_apply_end` | ファイル編集。実装フェーズの確定材料 |
| `event_msg` / `context_compacted` | 文脈圧縮の発生回数（参考指標） |
| `event_msg` / `mcp_tool_call_end` | MCP 呼び出し |

`token_count` の実測値:

```json
{ "info": {
    "total_token_usage": { "input_tokens": 156277149, "cached_input_tokens": 153804544,

**`total_token_usage` は累積値である。** セッション内で単調増加するため、
**最終行の値だけを採り、行ごとに加算しない。**
`last_token_usage` はターン単位の差分で、ターン別内訳に使う。

実測で確認した内訳の関係:

- `total_tokens = input_tokens + output_tokens` が厳密に一致した（156,277,149 + 268,251 = 156,545,400）
- `cached_input_tokens ≤ input_tokens`、`reasoning_output_tokens ≤ output_tokens` が成立した

> 要確認: 上の 2 つ目は「内数である」ことと整合するが、**大小関係の観測であって内数であることの証明ではない。**
> 課金相当の式（7.1）はこの前提に依存するため、Q1 として確認対象に上げる。

`session_meta` から取る項目:

| 項目 | 用途 |
|---|---|
| `session_id` | **重複排除の鍵**（→ 5.2） |
| `id` | ファイル固有の ID。`session_id` と異なる場合がある |
| `forked_from_id` / `parent_thread_id` | fork の判定・親子の紐付け |
| `cwd` | プロジェクト別集計 |
| `thread_source` / `agent_nickname` / `agent_path` | サブエージェントの識別と表示名 |
| `cli_version` / `originator` | バージョン別の傾向（任意） |

`custom_tool_call` の `input` は **JavaScript のラッパ文字列に JSON が埋まった二重構造**である。

```
const r = await tools.shell_command({"command":"rg -n \"…\" \"C:\\…\\MEMORY.md\"",
                                     "workdir":"C:\\ToolCreate\\Y_SmartApp","timeout_ms":10000}); text(r)
```

コマンド本体を取り出すには、`tools.shell_command(` の直後から対応する `)` までを切り出して
JSON としてパースする必要がある。**正規表現で `"command":"..."` を直接拾わない。**
コマンド内にエスケープされた `"` が含まれるため、非貪欲マッチでは途中で切れる。

## 5 正規化と重複排除

**本章がこの機能の中核である。** 履歴には同じ課金が複数回現れる。
除外しなければ、出てくる数字は実態の 2〜3 倍になる。

### 5.1 Claude Code — 同一応答が複数行に書かれる

1 つの API 応答が複数の content ブロックを持つ場合、**同じ `usage` を持つ `assistant` 行が
ブロック数だけ書き出される。**

実測（サンプル 1 セッション）:

| 観測 | 値 |
|---|---|
| `assistant` 行 | 357 |
| ユニークな `requestId` | 145 |
| 複数行を持つ `requestId` | 120 |
| そのうち **全行の usage が完全に同一** | **120 / 120** |

同一 `requestId` の 4 行が、`message.id`・`output_tokens`・`cache_read_input_tokens`・
`cache_creation_input_tokens` のすべてで一致していた。

除外しなかった場合の影響:

| 指標 | 全行合算 | `(requestId, message.id)` で一意化 | 倍率 |
|---|---|---|---|
| `output_tokens` | 1,166,378 | 498,755 | **2.34 倍** |
| `cache_read_input_tokens` | 128,303,401 | 52,361,741 | **2.45 倍** |
| `cache_creation_input_tokens` | 2,728,023 | 1,007,425 | **2.71 倍** |
| `input_tokens` | 657 | 267 | 2.46 倍 |

**採用する規則。** `(requestId, message.id)` の組を鍵とし、初出の 1 件だけを採用する。

`requestId` 単独ではなく `message.id` との組にするのは、
**1 リクエストが複数メッセージを返す形式が将来現れた場合に取りこぼさない**ためである。
実測範囲では両者は 1 対 1 だった。

> 注意: `requestId` を持たない `assistant` 行があり得る（キャッシュヒットや復元時）。
> **鍵が欠けている行は「一意」として扱い、必ず加算する。**
> 鍵が無いことを理由に捨てると、実在する消費を落とす。落とす方が過大計上より発見しにくい。

### 5.2 Codex — session_id は会話ツリーのルートであってセッションではない

> **Rev 1.2 で全面的に差し替えた。** Rev 1.1 は「fork のたびに元履歴が丸ごと複製される」という
> 前提に立ち、`session_id` を鍵にして最大値の 1 件だけを採る規則にしていた。
> B0 の実機確認（→ 10.2.2）でこの前提が誤りと分かったため、規則ごと入れ替えた。

Codex は 1 つの会話ツリーから派生したスレッド（fork とサブエージェント）に、
**同じ `session_id` を与える。** `session_id` はツリーのルート ID であり、セッションの識別子ではない。
スレッド固有の識別子は `session_meta.id` である。

実測（540 ファイル / 2026-09-01 時点）:

| 観測 | 値 |
|---|---|
| `session_id != id` のファイル | 364 |
| ユニークな `session_id` | 90 |
| 同一 `session_id` が複数ファイルに出現 | 34 件（**最大 76 ファイル**） |
| `forked_from_id` を持つファイル | 138 |
| `thread_source` の内訳 | subagent 404 / user 82 / automation 1 / なし 53 |
| **ユニークな `session_meta.id`** | **540（重複 0）** |

**同一 `session_id` のファイル群は複製ではない。** `user_message` の系列を全ペアで比較したところ、
検査した 12 グループすべてで prefix 関係が成立せず、**内容が枝分かれしていた**。

**fork 先は累積トークンをリセットして 0 から始まる。** 親を解決できた 390 スレッドのうち、
子の初回累積が親の累積の半分以上だったのは 3 件のみで、387 件は 1〜2 万トークン
（自分の初期コンテキスト相当）から始まっていた。
つまり各スレッドの `total_token_usage` は、そのスレッド固有の消費である。

**重複計上は存在しない。** 内容シグネチャ（`user_message` 列 + 最終累積 + 行数）が一致する
複製ファイルは **0 組**、全行が同一 timestamp のファイルも **0 件**だった。
`id` 単位の合算と内容一意化後の合算は完全に一致した（差 0）。

**採用する規則。** `session_meta.id`（スレッド固有 ID）を鍵とし、**すべてのスレッドを別々に集計する。**
`session_id` は親子表示のグルーピングにのみ使い、重複排除には使わない。

Rev 1.1 の規則を適用した場合の影響:

| 集計方法 | `total_tokens` 合計 | 判定 |
|---|---|---|
| `session_meta.id` で一意化（Rev 1.2） | 7,713,173,162 | **正しい** |
| `session_id` の最大値のみ採用（Rev 1.1） | 1,929,849,177 | **75% が消える** |

消えるのは主にサブエージェント分である（thread_source 別の内訳は
subagent 5,306,505,158 / user 1,894,521,090）。
**サブエージェントは「重複」ではなく「独立した消費者」として扱う。**
1.1 の動機(3)は、まさにこの消費を見えるようにすることだった。

> 教訓: ID の共有だけを根拠に除外規則を作らない。「重複しているはず」という仮説は、
> 内容シグネチャの一致で裏を取ってから規則にする。裏取りを省くと、実在する消費を捨てる。

時刻の種類が 1 つしかないセッションは**経過時間の算出から除外する**（測定不可として扱う）。
トークンは有効なので集計には含める。画面上は「測定不可」バッジを出す（→ 8.4）。
実機の 540 ファイルでは該当が 0 件だったが、規則としては残す。

### 5.3 プロジェクトの正規化

実測で `C:\ToolCreate\Y_SmartApp` と `c:\ToolCreate\Y_SmartApp` が別プロジェクトとして集計された。
それぞれ 15.1 億 / 10.7 億トークンで、本来は 1 つである。

**正規化の規則**（この順で適用する）:

| # | 処理 |
|---|---|
| 1 | ドライブレターを大文字化（`c:` → `C:`） |
| 2 | 区切りを `\` に統一（`/` を含む記録があり得る） |
| 3 | 末尾の区切りを除去 |
| 4 | **大文字小文字は 1 以外では変換しない** |

規則 4 の理由: Windows のファイルシステムは大文字小文字を区別しないが、
**全体を小文字化すると表示が読みにくくなる**（`c:\toolcreate\y_smartapp`）。
比較用の正規化キーと、表示用の原文を**両方保持する**。表示は最初に観測した表記を使う。

> 制約: 同じプロジェクトを異なる大文字小文字で記録した履歴が混在する場合、
> 表示名は「最初に観測した方」になる。**利用者の期待と異なる表記が出ることを受け入れる。** → C1

### 5.4 親子の紐付け

サブエージェントの消費を親に合算しないと実態が見えない（→ 1.1）。
一方で、合算だけにすると「どのサブエージェントが重いか」が見えなくなる。

**両方を保持する。** セッションレコードに親 ID を持たせ、集計時に 2 系統の値を出す。

| 指標 | 定義 |
|---|---|
| 単独値 | そのセッションだけの消費 |
| 累計値 | そのセッションと、配下の全サブエージェントの合計 |

プロジェクト別の集計には**単独値の総和**を使う（累計値を足すと二重計上になる）。
セッション一覧では**親行に累計値、子行に単独値**を出し、子は既定で畳む（→ 8.4）。

| ツール | 親子の判定 |
|---|---|
| Claude Code | ファイルパス（`<親UUID>/subagents/...`）と `isSidechain` |
| Codex | `session_meta.parent_thread_id` と `thread_source=subagent` |

        { "dateLocal": "2026-08-31", "turns": 14,
          "tokens": { "input": 267, "output": 498755, … } } ],
      "toolCounts": { "Bash": 48, "Edit": 36, "Read": 35, "Write": 8, … },
      "phaseCounts": { "investigate": 41, "implement": 44,
                       "test": 3, "dialogue": 2, "unknown": 3 },
      "unknownCommands": { "Get-Random": 2, "certutil": 1 },  // 語彙追加の手掛かり（上位20件）
      "dedup": { "rawRecords": 357, "acceptedRecords": 145,
                 "duplicateFiles": 0 },   // Codex の fork で除外したファイル数
      "parseErrors": 0,
      "lastLineBroken": false }       // 末尾行が壊れていた（値が古い可能性）
  ]
}
```

設計上の要点:

| 事項 | 決定 |
|---|---|
| 保持するのは集計済みレコードのみ | ターン単位の明細は保持しない。ターン別明細そのものを N9 で非スコープにしたため、保持する動機が無い |
| モデルはセッション内で 1 つに固定しない | Codex は `turn_context` でターンごとに変わり得る。`byModel` で内訳を持ち、S5 のモデル別集計と付録 B.1 の再現に使う |
| 日またぎ | `byDay` に分割して持つ。セッション合計だけでは日別グラフを作れない（→ 7.4） |
| `unknownCommands` | 未分類コマンドの語彙をここに残す。`toolCounts` は Codex では `{"exec": N}` にしかならず、7.3.4 のトップ 20 を作れない |
| `skipReason` | 読めなかったファイルはセッションを作れない。`files` 側に理由を残す |
| `lastLineBroken` | Codex は最終行の累積値だけを採る（4.2）。末尾が壊れたファイルは**エラーにならず静かに過小計上**されるため、フラグで区別する |
| `schemaVersion` | 分類ルールや指標定義を変えたら上げる。**版が違えば全件再パースする** |
| 削除された履歴ファイル | `files` から消えても `sessions` は残す。過去分を失わないため |
| 書き込み | 一時ファイルへ書いてから `File.Replace` で置換する。既存の `.bak` は毎回上書きしてよい（世代管理はしない） |
| 書式 | `WriteIndented = false`、`Encoder` は既定（→ 3.3.2） |

> 注意: `phaseCounts` は**ツール実行の回数**であって時間ではない。
> Rev 1.0 では `phaseSec`（秒）を持たせていたが、**ツール実行 1 回を何秒に帰属させるかの規則が
> どこにも書かれておらず、S7 の中核が空だった。**
> Rev 1.1 で回数ベースに統一した。画面のフェーズ内訳も「回数の構成比」として出す（→ 8.2 / 付録 D）。

## 7 集計仕様

### 7.1 トークン指標の定義

キャッシュ読込は実際のモデル処理には効くが、課金・レート制限への寄与は小さい。
**両方を別々に出す。片方だけを「トークン数」と呼ばない。**

| 指標 | Claude Code | Codex |
|---|---|---|
| 課金相当トークン | `input + cache_creation + output` | `(input − cached_input) + output` |
| 総処理トークン | 上記 + `cache_read` | `input + output`（= `total_tokens`） |
| キャッシュ読込 | `cache_read_input_tokens` | `cached_input_tokens` |
| 推論トークン | 記録なし（`-` を表示） | `reasoning_output_tokens`（`output` の内数として別掲） |

実測では総処理トークンの 95〜97% がキャッシュ読込だった。
**単純合計を「使用量」として出すと、実感（レート制限の消費）と桁が合わない。**
概要画面では課金相当を主指標とし、総処理トークンは併記に留める（→ 8.2）。

> 要確認: Codex の課金相当を `(input − cached_input) + output` としたのは、
> `cached_input` が `input` の内数であるという前提に立つ。**この前提は未検証。** → Q1

### 7.2 時間の定義

| 指標 | 定義 |
|---|---|
| 経過時間 | セッション内の最初の記録と最後の記録の時刻差 |
| 測定可否 | 記録の時刻が 1 種類しかないセッションは「測定不可」とする（→ 5.2） |

**経過時間だけを出す。推定は行わない。**

> 制約: 経過時間には、人間が読んでいる時間・離席・別作業が含まれる。
> **これは「作業時間」ではない。** 画面でも「経過時間」と表記し、作業時間と呼ばない。→ C5

Rev 1.0 では、隣接する記録の時刻差からしきい値超の空白を除いた「アクティブ時間」を出す設計にしていた。
Rev 1.1 で取り下げた。理由は 3 つある。

- しきい値（120 秒）に実測の根拠が無く、**実装前に潰すべき Q を 1 つ増やしていた**
- 長時間かかるビルド・テストが「離席」として除外され、**テストフェーズだけが系統的に過小になる**
- 要求は「使用量の統計・プロジェクト分析・履歴」であり、経過時間で足りる

空白時間の分布を測ってから入れる。**測らずに閾値を置かない**（→ 付録 D）。

### 7.3 フェーズ分類と信頼度

ツール実行を 5 区分へ写像し、**回数で数える。** 時間へは変換しない（→ 7.2）。
**分類は推定であり、分類できないものを「その他」に押し込まない。**
決められないものは `unknown`（未分類）として明示的に数える。

### 7.3.1 Claude Code の分類規則

ツール名が直接記録されるため、規則は素直になる。

| フェーズ | 対象ツール |
|---|---|
| 調査 | `Read` `Glob` `Grep` `WebFetch` `WebSearch` `NotebookRead` `Task`（探索系） |
| 実装 | `Edit` `Write` `MultiEdit` `NotebookEdit` |
| テスト | `Bash` / `PowerShell` のうち、コマンドが 7.3.3 のテスト語彙に一致するもの |
| 対話 | `AskUserQuestion` `TodoWrite` |
| 未分類 | 上記以外の `Bash` / `PowerShell`、`mcp__*`、未知のツール名 |

実測サンプルでの分類率は **94.1%**（`mcp__ccd_session__mark_chapter` 1 件のみ未分類）。

### 7.3.2 Codex の分類規則

`custom_tool_call` はすべて `name=exec` であり、ツール名からは何も分からない。
**4.2 の手順でコマンド本体を取り出してから語彙で判定する。**

| フェーズ | 判定 |
|---|---|
| 実装 | `patch_apply_end` イベント（ツール実行ではなく結果イベントで確定できる） |
| テスト | コマンドが 7.3.3 のテスト語彙に一致 |
| 調査 | コマンドが 7.3.3 の調査語彙に一致 |
| 未分類 | 上記以外 |

**Windows 環境では中身が PowerShell である。** 実測で観測されたのは
`Get-Content` / `Select-Object` / `Select-String` / `$p='...'; ...` の形で、
`cat` / `grep` を前提にした語彙表では拾えない。

初期の素朴な規則（POSIX 語彙のみ）を全 505 ファイルに当てた結果:

| 分類 | 件数 |
|---|---|
| 未分類 | **12,206** |
| 実装（パッチ適用） | 4,103 |
| 調査 | 780 |
| テスト / ビルド | 299 |

分類率 41.7%。**PowerShell 対応は必須であり、それでも Claude Code の水準には届かない見込みである。**

**Rev 1.2 の実測（実装後）。** PowerShell 語彙の追加に加え、次の 2 点で分類率が上がった。

| 対策 | 効果 |
|---|---|
| `cd` / `Set-Location` / 変数代入などの前置きを読み飛ばし、次のコマンドで判定する | 先頭が `cd` のコマンドを拾えるようになった |
| **パッチ適用を要求側で分類する**（`custom_tool_call` の `name=apply_patch`、および `name=exec` で input が `*** Begin Patch` 本文のもの） | 未分類 3,050 件が実装へ移った |

| 対象 | Rev 1.1 時点 | Rev 1.2 実測 |
|---|---|---|
| Codex | 41.7% | **74.2%**（実行 15,645 回 / 未分類 4,036 回） |
| Claude Code | 94.1%（サンプル 1 セッション） | 80.3%（実行 29,127 回 / 未分類 5,751 回） |
| 全体 | — | 78.3% |

> 注意: **パッチ適用は要求（`custom_tool_call`）と結果（`patch_apply_end`）の両方が記録される。**
> 両方を数えると 1 回の編集が 2 回の実行になるため、**回数の基準を「要求」に統一した**
> （`exec` も要求で数えているため基準が揃う）。Rev 1.1 の 7.3.2 は結果イベントで数える設計だったが、
> Rev 1.2 で要求側へ変更した。
>
> Claude Code の 94.1% は 1 セッションのサンプル値であり、全履歴では 80.3% だった。
> 未分類の主因は `mcp__*` 系ツールと、語彙表に無い Bash / PowerShell コマンドである。

### 7.3.3 語彙表

**`PhaseClassifier` 内の定数として持つ。外部設定ファイルにはしない。**
7.3.2 の通り、PowerShell に対応しても Claude Code の水準には届かない見込みの機能である。
そこへ外部ファイル・設定 UI・形式互換の 3 つを先回りで足さない（→ N12）。
語彙を増やす必要が出たら、`unknownCommands`（6 章）を見てコードを直し、再ビルドする。

初期値:

| フェーズ | POSIX / 汎用 | PowerShell |
|---|---|---|
| 調査 | `rg` `grep` `ls` `cat` `head` `tail` `find` `fd` `wc` `git log` `git status` `git diff` `git show` | `Get-Content` `Select-String` `Get-ChildItem` `Measure-Object` `Select-Object` `Get-Item` |
| テスト | `dotnet test` `dotnet build` `msbuild` `pytest` `npm test` `npm run build` `go test` `cargo test` `cargo build` | `Invoke-Pester` |

判定はコマンド文字列の**先頭トークン**に対して行う。パイプで繋がっている場合は先頭のみを見る。

> 制約: パイプの先頭だけを見るため、`Get-Content x | Where-Object …` は調査、
> `dotnet build | Select-String error` はテストと判定される。**後段の意図は反映されない。** → C3

### 7.3.4 信頼度の提示

**分類率を必ず画面に出す。** 出さないと、41.7% の推定値が確定値として引用される。

| 分類率 | 表示 |
|---|---|
| 80% 以上 | 緑。そのまま提示 |
| 50% 以上 80% 未満 | 黄。「参考値」と併記 |
| 50% 未満 | 赤。フェーズ別グラフの上に警告帯を出す |

未分類コマンドの出現回数トップ 20 を「ツール内訳」タブに出す（6 章の `unknownCommands`）。
**次の版で語彙表に何を足せばよいかが分かる形にする。**

### 7.4 日付軸への帰属

セッションは日をまたぐ。実測では 505 セッションの経過時間合計が 1,812 時間（平均 3.6 時間）で、
124 分を超えるセッションも観測している（付録 B.1）。**またぎは確実に起きる。**

| 事項 | 決定 |
|---|---|
| 日別集計の単位 | **セッションではなくターン。** 各ターンの開始時刻が属する日へ計上する |
| タイムゾーン | 履歴の `timestamp` は UTC。**日付境界はローカル時刻**で切る |
| 期間セレクタの判定 | セッションの**開始時刻**で絞る。またいだセッションは開始日の側に含める |
| 按分 | 行わない。ターン単位で切れば按分は不要になる |

> 注意: 「日別グラフの合計」と「期間で絞ったセッション一覧の合計」は**一致しない。**
> 前者はターン単位、後者はセッション単位で切っているためである。
> 画面では両方に「ターン基準」「セッション基準」を明記する。
> 一致させようとしてどちらかに寄せると、日またぎのセッションが日別グラフから消えるか二重に出る。

### 8.1 画面構成

単一 HTML の中でタブを切り替える。ページ遷移は無い。

プロジェクト表に「全件表示」トグルを付ければ足り、列も操作も同じ画面を 2 つ持つ理由が無い（→ N13）。

まず当日の使用量を見て、必要に応じて範囲を広げる流れにする。

「今日」のように対象が 1 日しかない期間では、**日別グラフのブロックごと隠す**。
棒 1 本のグラフから読み取れることが無いためである。KPI とプロジェクト表で足りる。
期間内に履歴が 1 件も無いときは、概要タブの先頭に「この期間に記録された履歴はありません」と出す。

### 8.1.1 画面に出す言葉

**設計上の呼び方をそのまま画面に出さない。** 集計の正確さは定義で担保し、
画面では日常の言葉を使う。対応は次のとおり。

| 設計上の呼び方（本書） | 画面の表示 | 画面に添える説明 |
|---|---|---|
| 課金相当トークン | **消費トークン** | 使用量の枠（レート制限）を減らす分。キャッシュから読んだ分は含みません |
| 総処理トークン | **処理トークン** | AI が実際に読み書きした量。うちキャッシュから読んだ分が N |
| フェーズ | **何をしていたか** | ツールを実行した回数の割合です。かけた時間ではありません |
| フェーズ分類率 | **作業内容の判別率** | ツール実行のうち、何の作業か分かったものの割合 |
| 単独値 / 累計値 | **その子だけの分 / 子を含めた合計** | — |
| 未分類コマンド | **判別できなかったコマンド** | — |

本書の本文では設計上の呼び方を使い続ける。**画面の文言を変えるときは、この表も併せて直す。**
片方だけ変えると、レビューのときに画面と設計書が別物に見える。
**再スキャン・CSV 出力のボタンは置かない。** HTML は外部通信も C# 呼び出しも持たないため実行できず、
押せないボタンを置くと利用者を迷わせる。更新は AIUsageOverlay のトレイメニューから行う旨を
ヘッダに 1 行で書く。

| 期間セレクタで 0 件になった | 「該当なし」を表示。直前の描画を残さない |
| 選択中のセッションが期間外になった | 選択を解除する。**期間は自動で戻さない** |
| ファイルが別プロセスにロックされている | そのファイルをスキップし、`skipReason` に理由を残す。次回スキャンで再試行 |
| JSON として壊れた行 | その行のみスキップ。`parseErrors` に計上 |
| **末尾行が壊れている**（書き込み途中を読んだ） | `lastLineBroken = true`。Codex は最終行の累積値を採るため、**エラーにならず過小計上になる。** 画面にバッジを出す |
| **スキャン中に履歴ファイルが更新された** | 読み取り前後の `(size, mtime)` が変わっていたらキャッシュに登録しない。次回スキャンで読み直す（→ 3.4） |
| **AIUsageOverlay が多重起動している** | `learnings.md` の記録の通り Mutex は未実装で、実際に 2 プロセス常駐が観測されている。キャッシュ書き込みを**名前付き Mutex で保護する。** 取得できなければレポート生成を中止し、「別のインスタンスが集計中です」と出す |
| キャッシュの `schemaVersion` が異なる | 全件再パースする。利用者に確認しない（可逆であり、結果は同じになるため） |
| キャッシュが壊れている | 破損キャッシュを `.bak` へ**上書き退避**し、全件再パースする（世代管理はしない） |
| 置換前に落ちて一時ファイルが残った | 次回起動時に削除してから書き始める |
| 生成中に再度メニューを押された | 二度目を無視する。メニュー項目を実行中は無効化する |
| レポートの出力先が書き込めない | エラーダイアログを出し、既定ブラウザは開かない |

### 8.7 埋め込み JSON のエスケープ

集計結果の JSON には、履歴由来の任意文字列（指示文・フルパス・未分類コマンド）が入る。
**`<script>` に素で書き出すと、指示文に `</script>` が含まれた時点で HTML が破綻し、
任意スクリプトが実行され得る**（→ R6）。

| 事項 | 決定 |
|---|---|
| 埋め込み先 | `<script type="application/json" id="report-data">…</script>`。**実行可能な `<script>` に直接書かない** |
| 読み出し | `JSON.parse(document.getElementById('report-data').textContent)` |
| 追加エスケープ | JSON 化した文字列に対し `<` → `<`、`>` → `>`、`&` → `&`、`\u2028` / `\u2029` を置換する |
| 適用箇所 | **1 箇所に集約する。** 埋め込み処理を通らない書き出し経路を作らない |
| 検証 | T14 で `</script>` `<!--` `\u2028` を含む合成データを通す |

`<` を潰せば `</script>` は成立しない。`&` は HTML エンティティ解釈、`\u2028` / `\u2029` は
JavaScript の行終端子として扱われるため、いずれも JSON としては合法だが埋め込むと壊れる。

### 8.8 グラフの描画方式

外部参照が 0 件であること（T13）から、**CDN のチャートライブラリは使えない。**
ライブラリをテンプレートへインライン展開する案も、数十〜数百 KB がレポートごとに複製されるため採らない。

**必要なグラフは 3 種類だけである。いずれも手書きの SVG で足りる。**

| グラフ | 描き方 |
|---|---|
| 日別の積み上げ棒 | `<rect>` を日数ぶん並べる。目盛は最大値から線形に 4 本 |
| フェーズ・構成比の横帯 | `<rect>` を横に並べる。幅は構成比 |
| 表内のミニ構成比バー | 同上。1 行あたり 4 個 |

円グラフ・折れ線・散布図は使わない。**弧の計算とツールチップの実装が必要になる割に、
上の 3 種類で読み取れることが増えない。**

描画はブラウザ側の JS で行う（期間セレクタで再描画するため）。
JS は `<script>` に直接書き、**データだけを 8.7 の方式で分離する。**

### 8.9 レポート未生成の通知

**なぜ要るか。** 履歴ファイルは各ツールの保持期間で削除される。
本機能のキャッシュは一度取り込んだセッションを保持し続けるため（→ 6 章「削除された履歴ファイル」）、
**レポートを生成した時点までの記録は残る。** 逆に言えば、
**生成しないまま履歴が消えた分は復元できない。**

| 事項 | 決定 |
|---|---|
| 判定 | 設定に持つ最終生成日時と現在時刻の差が、しきい値（既定 7 日）以上か |
| 未生成の場合 | 一度も生成していないときも対象にする。「早めに一度生成しておくと過去分を残せます」と出す |
| タイミング | **既存の更新確認タイマー（6 時間周期）に相乗りする。** 専用タイマーを増やさない |
| 頻度 | **同じ起動中は 1 回だけ。** 6 時間ごとに繰り返し出さない |
| 通知手段 | 既存の `NotificationService`（トレイのバルーン）。外部通信は行わない |
| 設定 | 「レポート未作成を通知する」（既定 ON）。しきい値の日数は設定 UI に出さず、`settings.json` の値を使う |
| 生成成功時 | 最終生成日時を保存し、通知フラグを戻す |

> 注意: **通知は「押し忘れ」を減らすだけで、取りこぼしを無くすものではない。**
> 確実にするには、レポートを開かずキャッシュだけを定期的に更新する仕組みが要る
> （実測ではフルスキャン 7 秒、差分ならそれ以下）。本 Rev では入れていない。
> 入れるかどうかは、通知の運用実績を見てから判断する。

### 10.2 要確認事項の詳細

### 10.2.1 Q1 — Codex の cached_input が input の内数か

**分かっていること。** 実測 1 セッションで `total_tokens = input_tokens + output_tokens` が
厳密に一致した（156,277,149 + 268,251 = 156,545,400）。また
`cached_input_tokens`（153,804,544）は `input_tokens`（156,277,149）より小さかった。

**分からないこと。** 大小関係が成立することは内数であることの証明ではない。
`cached_input_tokens` が独立にカウントされた別枠で、たまたま小さいだけの可能性を排除できていない。**未確認。**

**放置するとどうなるか。** 7.1 の課金相当を `(input − cached_input) + output` としているため、
外数だった場合は引いてはいけないものを引き、**課金相当が大幅な過小計上になる。**
過小計上は「使っていないはずなのに枠が尽きる」という形で現れ、原因の特定が難しい。

**どう確かめるか。** キャッシュが効かない新規セッションを 1 つ作り、`cached_input_tokens` が 0 の状態で
`input_tokens` を記録する。続けて同じ文脈で 1 ターン進め、`input_tokens` の増分と
`cached_input_tokens` の値を突き合わせる。内数なら増分の内側に収まる。

### 10.2.2 Q2 — Codex の fork が枝分かれし得るか

**分かっていること。** 実測 505 ファイル中 125 が `forked_from_id` を持ち、
同一 `session_id` が最大 76 ファイルに複製されていた。5.2 では
「同一 `session_id` のうち `total_tokens` 最大の 1 件を採る」規則にしている。

**分からないこと。** 同じ親から独立した 2 つの枝が伸びた場合、両者は同じ `session_id` を持つのか、
それとも別 `session_id` になるのか。**未確認。**
同じ `session_id` を共有するなら、最大値だけを採ると他方の枝の消費が落ちる。

**放置するとどうなるか。** サブエージェントを並行起動する使い方をしたときだけ過小計上になる。
実測ではサブエージェントが親の 100 倍以上を消費した例があるため、**落ちる量が大きい。**
しかも並行起動しない日は正しい値が出るので、誤りに気付きにくい。

**どう確かめるか。** 1 つの親セッションからサブエージェントを 2 つ同時に起動し、
生成された rollout ファイルの `session_id` と `parent_thread_id` を比較する。
別 `session_id` なら現行規則で足りる。同一なら `id`（ファイル固有 ID）を第 2 鍵に加える。

### 10.2.3 Q7 — 親セッション単体の消費はサブエージェントより小さいか

**分かっていること。** 実測で、同一プロジェクト・同一時間帯に動いた 2 つのサブエージェントが
2,166 万トークンと 17 万トークンを消費していた（付録 B.1）。**サブエージェント間で 125 倍の差がある。**
5.4 では、親に累計値、子に単独値を併記する設計にしている。

**分からないこと。** 親セッション単体の消費量。**未計測。**
Rev 1.0 では「親 17 万に対し子 2,166 万」と書いていたが、**17 万の行もサブエージェントであり誤読だった**
（→ 付録 D）。親が子より軽いという前提は、実測では裏付けられていない。

**放置するとどうなるか。** 1.1 の動機(3)と 5.4 の親子併記が、根拠を欠いたまま実装される。
親が実は重いのであれば、既定で子を畳む 8.4 の一覧設計が実態を隠すことになる。
**「サブエージェントが見えない」という問題設定自体が誤りだった、という結論もあり得る。**

**どう確かめるか。** B2 の実装後、親子を紐付けた集計を実データに当て、
親の単独値と配下の合計を並べて出す。親が支配的なら 8.4 の既定を「子を開く」に変える。

### 11.2 既存実装との突合

突合対象は無い（新規機能のため）。代わりに、**本設計の起草に使った実測スクリプトの出力を基準値とする。**
付録 B の数値を再現できることをもって、読み取りロジックの正しさとする。

突合するときに揃えないと必ず不一致になる点:

- 期間の境界（UTC かローカルか）。**履歴の `timestamp` は UTC。集計の日付境界はローカル**にする
- `total_token_usage` を最終行から採るか全行合算するか（4.2）
- サブエージェントを含めるか（5.4 の単独値／累計値）

### C.1 rate_limits によるスクレイピング置き換え

Codex の履歴に、レート制限の使用率がそのまま記録されていることを確認した。

```json
"rate_limits": { "primary":   { "used_percent": 93.0, "window_minutes": 300,   "resets_at": 1788162990 },
                 "secondary": { "used_percent": 15.0, "window_minutes": 10080, "resets_at": 1788749790 },
                 "plan_type": "plus" }
```

`primary` が 5 時間枠、`secondary` が週枠に対応する。
現在 `CodexWebScraper` が WebView2 経由で取得している値を、**ローカルファイルの読み取りで置き換えられる可能性がある。**

送った理由と、置き換える場合の制約:

- 値が更新されるのは **Codex を実行したときだけ**である。常駐監視の用途では「最後に使った時点の値」になる
- したがって単純な置き換えではなく、「スクレイピング成功時は実測値、失敗時は履歴の最終値をフォールバックとして出す」
  という併用設計になる。**これは既存のちらつき防止フラグ（`_gitHubEverLoaded` 等）の設計と干渉する**
- 本 Rev のスコープ（事後分析）と目的が違うため、混ぜると両方の受け入れ判定が曖昧になる

> 制約: 本 Rev では実装しない。**この付録は、次に検討するときの出発点として残す。**
